Warranty Claims Agent

A multimodal agent built with Claude Code: computer vision (PatchCore), deterministic policy, and LLM agents orchestrated with LangGraph  ·  DriveNets AI Specialist Engineer assignment  ·  October 2026
Repository: github.com/HayLahav/Warranty-Claims  ·  Demo video: English  ·  Hebrew

1. Executive summary

Problem. The starting point was a project of my own, built earlier: a text-only LangGraph agent that answered questions about a customer-support dataset (Bitext). It could talk about refunds but could not see a product. A large share of real support volume is warranty claims, where the deciding evidence is a photo: is the product actually defective? Letting an LLM look at the photo and decide is the obvious approach, but it is hard to verify and easy to talk into a refund.

Goals. (1) Real computer vision whose decisions can be checked against pixel-level ground truth. (2) LLMs handle language only and never make the financial decision. (3) Every failure path is fail-closed: an error can never approve or reject a claim, only escalate it to a human. (4) Honest, cross-validated metrics, plus an analysis of why the system fails where it fails. (5) A visual demo.

Architecture. A customer submits a message, a photo and the product on their order. A LangGraph state machine runs the agents in sequence:

  • Inspector: PatchCore (anomalib, WideResNet-50, 10% coreset). It is fitted on defect-free images only and returns an anomaly map and the share of the photo flagged. There is one model per product. The claim score is the map's maximum inside the segmented product, so lint or dust on the backdrop cannot decide a claim.
  • Policy: pure Python. A calibrated uncertainty band per product: approve above it, reject below it, escalate inside it. An out-of-distribution guard escalates photos that don't look like the ordered product, and a coverage check escalates photos where the product could not be cut out plausibly. Malformed input or failures go to NEEDS_INFO or ESCALATE, never to APPROVE or REJECT.
  • Router / Responder: Nemotron 3.5 Lightning on Nebius Token Factory. The responder must open with a fixed status line, and a deterministic post-check rejects any reply that contradicts the verdict (retry, then a template).
  • VLM cross-check: GLM-5.3-Flash looks at escalated photos only and writes a note for the human specialist. It never sees the customer's text and never changes the verdict.
  • Claims Analyst: a chat agent that answers questions about the evaluation results. It only chooses tools and phrases answers. Every number comes from deterministic tools over the result files, and a grounding check rejects numbers found in no tool result.

Dataset. MVTec AD. I chose it over the VQA benchmarks an AI assistant suggested because it has pixel-level defect masks, so every decision can be checked against ground truth. I deliberately picked two categories that are structural opposites, rather than a sample of the benchmark:

  • bottle (83 test images): a rigid body with a smooth, uniform surface and large, visible defects (broken rim, contamination). Its classes separate perfectly on anomaly score, so this is where automation should be fully confident.
  • screw (160): a small metallic object in arbitrary rotation, with fine structure and small, high-frequency thread defects. Its classes overlap, so this is the case that exercises escalation, calibration and error analysis. (Rotation turned out not to explain the errors; defect size does. See §5.)

Two categories also kept the full loop (fit, cross-validated calibration, error analysis, golden tests) within the deadline and a CPU-only laptop. Scaling to the full benchmark is the next phase (§6).

2. Prompts and development process

How I worked with Claude Code

  • Design before code. I used a brainstorming workflow: Claude Code proposed 2–3 approaches with trade-offs, and we agreed the design section by section (architecture → components → policy → testing). It was written to docs/plans/ and committed before any implementation.
  • Constraints, not instructions. The prompts that mattered most stated constraints ("LLMs never make the financial decision", "errors must never approve"). These turned into testable properties.
  • A running record of mistakes. docs/dev-log.md records every bug, wrong AI output and verification as it happened. Most of this document is drawn from it.
  • I asked "why". Several of the most important changes started with a question rather than an instruction.

3. Critical reflection: evaluating and improving the AI's output

The principle I followed: passing tests is evidence, reading the output is verification, and a number is only trusted after it has been checked against something independent. These are the cases where that mattered most.

3.1 The responder invented inspection findings, and every automated check passed

"We see that the bottle has a crack on the rim, which our visual inspection identified as a defect."

The inspector only reports that there is a defect and how much of the photo it covers. "Crack on the rim" came from the customer. The status line was right and no forbidden phrase appeared, so the deterministic post-check passed it. I only found it by reading the live replies.

Measured before fixing: a probe for sentences that mention the inspection and repeat a customer-supplied detail without attributing it ("you reported…") flagged 3 of 10 replies. I added prompt rule 5, and the count became 0 of 10. It is now a live eval (pytest -m live, 15 real calls). Later the eval itself failed on "we have reviewed your report of a crack". That reply is correct, so it was a false positive in my detector. I widened the attribution pattern and confirmed in both directions that it still flags the original hallucination. Loosening an eval needs a documented reason, so the change is logged.

3.2 Probing an "accepted risk" revealed that any photo could get a refund

The design listed "photo matches the ordered product" as an out-of-scope risk, on the assumption that the worst case was a missed detection. Before writing adversarial tests I probed it: a bottle claim with a photo of a screw scored 94 → APPROVE. PatchCore scores anything unfamiliar as very anomalous, so any photo got an automatic refund, the exact outcome fail-closed was meant to rule out. Score alone could not separate the cases (real bottle defects reach 76), but flagged area could: real defects cover at most 43% (bottle) and 2% (screw) of the photo, while wrong objects cover 91–100%. Fix: escalate when the area exceeds 1.5× the largest real defect. Verified on 12 photos from 4 MVTec categories never used in calibration: 26/26 escalated; with the guard removed, 26/26 auto-approved.
Lesson: listing a risk is not the same as knowing its consequence. The risk register gets probed, not just written.

3.3 Plots that showed something false

  • A scatter labelled REJECT (n=1) showed two violet points. A data query confirmed there was one image. The second "point" was the legend marker drawn inside the plot. All legends were moved outside the plot area.
  • The heatmap overlay tinted every photo blue, hiding what it was meant to show. Fixing it revealed a real finding: on the hardest screws the anomaly hotspot sits on the background, not on the labelled defect, even though pixel AUROC is 0.99. Easy cases dominate the aggregate metric.
  • The demo heatmaps still looked wrong when I reviewed them. I asked for a way to inspect all outputs instead of the 6 in the figure. Claude Code built a gallery of all 243 test images and a per-image check: does the map's hottest point land on the labelled defect? It found two things. (1) A bug: heatmap files were named by file number, and MVTec reuses numbers across defect types (good/000.png, broken_large/000.png), so claims overwrote each other's heatmaps. They are now named by a hash of the photo, with a test. (2) A display effect, not a model error: on the fixed colour scale, any bottle defect (scores 40–76 against a threshold of about 36) saturates a region far larger than the break. A per-image scale shows the peak inside the defect.

3.4 Checking claims that came in with my own prompts

My model-switch prompt said Lightning runs at "~314 tok/s" and would "eliminate latency". Throughput per token was not the issue: the model reasons silently and produced 6× more tokens than the previous model. Out of the box, the live eval went from 55 s to 173 s. Claude Code measured three ways to disable reasoning. Two (/no_think, reasoning_effort) did nothing; one (enable_thinking: false) brought it to 0.6 s per call and 14 s for the live eval. Because a new model can bring back old failures, the router and responder evals were rerun before committing. The same prompt said the text agents were on Gemma-3. They were not, and Claude Code corrected that rather than carrying it forward.

3.5 Reading the VLM's descriptions, not just its yes/no answers

In the first evaluation (47 escalations) the VLM's "defect visible" agreed with ground truth 77% of the time, and I read all 47 descriptions: about 3 of the 21 hits put the defect in the wrong place ("a fiber near the tip" on a screw whose head is scratched): the right answer for the wrong reason. A boolean metric scores these as correct.

After the scoring change (§5) I re-ran it on the new 54 escalations. The numbers jumped (defects seen 21/30 → 30/34), which was suspicious, so the identical 98 calls were run a second time. The "defect visible" answer changed on 9 of the 54 escalations (62/74 agreement on real photos), even at temperature 0, while "is this the right product?" agreed 98/98. Part of the jump was the new image set and part was run-to-run noise. A single run cannot tell them apart. Decision: the VLM stays a note for the specialist. Letting it approve would auto-approve 4/20 good escalated screws (the current system: 1/41), and on about one escalation in six its defect opinion is effectively a coin flip. Its product check is reliable. The specialist panel now says this. A first re-run also failed outright (98/98 calls unavailable, probably rate-limiting) and silently overwrote the previous results. The evaluation now records each call's error and refuses to write results when more than 10% of calls fail.

3.6 The Claims Analyst: correct numbers, wrong conclusions

The Claims Analyst follows the project rule: the LLM never produces numbers. Deterministic tools compute everything. Its live eval checks two things for each question: the expected facts (derived from the result files), and that every number in the answer appears in a tool result. On the first run, 3 of 6 questions failed, and each failure taught something different:

  • No tool, invented number: "The escalation rate for screw is 12.5%" (true: 33.8%). No tool had been called.
  • Generalising from a truncated list: the claim-listing tool showed the 10 lowest-scoring escalations, which were all good screws, so the model announced that all 54 escalations were good (true: 20).
  • Misreading a table: asked which defect type escalates most, it answered thread_top, quoting its correct 1/23. That is the least escalated type. Every number was grounded, and the conclusion was still wrong.

The fixes went into the tools, not the prompt. List tools now report the breakdown of all matches. The defect-type table includes an escalation-rate column and is sorted by it, so "most" means reading the first row. On top of that comes a deterministic grounding check, built like the responder's post-check: an answer with a number found in no tool result is retried once with a correction, then shown with a visible warning. Its unit test caught a bug in the check itself: the correction message quoted the rejected number, and user messages counted as sources, so a repeated invention looked grounded. After the tool changes, the check never fired in 18 live answers, and the eval passed 7/7 in repeated runs. One further error was grounded but mislabelled: "56.5% of all screw images" was really thread_side's escalation rate. The fix was renaming the column to pct_of_this_type_escalated, plus a regression case. A screenshot review of the finished UI caught one more: asked why the two errors happened, the model said both scores "sat in the escalation band", when both were decided automatically. The tool now states a computed explanation for each error, and a live regression test checks for that claim. A grounding check verifies numbers, not meaning; the fact checks are what catch the rest.

3.8 What I would do differently

  • Probe each "accepted risk" at design time, not after the pipeline was built.
  • Run integration smoke tests in the target environment (Jupyter/Colab) from the start (§4.4).
  • Add a safety margin around the band: both out-of-fold errors are exactly the two images that define its edges.

How they fit together: unit and integration run on every change (pytest default, ~20 s). Golden and eval run before a commit that touches the model, thresholds or graph. Live runs after any prompt or model change. Golden expected verdicts come from MVTec labels, never from model output, so a test cannot be written to match whatever the model happens to do.

Testing the tests. A test that passes the first time proves little. Safety tests were checked by mutation: I introduced the fault on purpose and confirmed a test failed. Examples: >= → > at the band edge; removing the isfinite guard (without it, a broken inspector returning +inf is auto-approved); removing the area guard (26 golden failures); letting the VLM approve; sending the customer's text to the VLM; removing the responder post-check. Each one was caught.

4.2 What I chose not to test, and the risks I accept

Not verifiedWhy / accepted risk
Real customer photos (phones, angles, lighting, backgrounds)MVTec contains only studio images and no such dataset with ground truth exists here. This is the largest gap: real deployment would need a new calibration set. The area guard limits the damage (unfamiliar photos escalate), but in-distribution miscalibration would not be detected.
Bottle threshold robustnessThe two bottle classes separate perfectly, so the band has zero width and nothing escalates. "0/20 good bottles approved" has a 95% CI up to 16%: only 20 good images exist.
Product segmentation on real photosThe score now ignores the backdrop (§5), but the segmentation assumes a dark product on a light backdrop. On a hazelnut photo with a dark background it took almost the whole frame as "the product", and the coverage (65%) was still inside the bottle's plausible range. The whole-photo wrong-object guard caught it, which is why that guard runs first. A cluttered real photo could defeat both, which is a strong reason for a real-photo calibration set.
Foreign objects that resemble the productTested with clearly different objects only. A bottle-like object could flag less area and pass.
Paraphrased promises in repliesThe blocklist catches known phrasings, not e.g. "your money is on its way" on an escalation. An LLM judge would be non-deterministic. Accepted, with a template fallback as the backstop.
Reply tone and qualityManual only. Known cosmetic issues: a repeated "a specialist will review"; "sorry the bottle arrived damaged" on a hazelnut photo.
Fraud (reused or stock photos), load, latency SLOsOut of scope for a demo; each needs its own system.
Router accuracy at scaleSpot-checked (5/5 including injection). An unclassifiable message fails closed to ESCALATE, so a routing error costs a human review, not money.
Loading the model file executes pickle codeThe model loader requires TRUST_REMOTE_CODE. Accepted because model files only come from our own Colab run.

4.3 Bugs the tests caught

  • CAUGHT Exported model would not load. The fit → export → load smoke test failed with a TRUST_REMOTE_CODE error. Without it, this would have surfaced on Colab after the full fit.
  • CAUGHT Fold leakage across products. Adding bottle changed screw's folds and therefore its reported metrics. Caught by a unit test while building the evaluator; folds are now assigned per product.
  • CAUGHT A wrong assumption, not a code bug. I asserted that no held-out good image is ever auto-approved. The test failed: the highest-scoring good image, held out, lies above a band calibrated without it. The expectation was wrong, and it showed early that in-sample "100% approve precision" does not survive cross-validation.

4.4 Bugs that slipped past, and what changed

  • SLIPPED Colab crash (RecursionError). The fit passed the local smoke test but crashed on Colab. Lightning's rich progress bar wraps stdout; inside Jupyter, the coreset loop's tqdm output writes back into the proxied stream and recurses. The test ran in a terminal, the code ran in Jupyter. Reproduced in a local kernel, fixed with one variable (enable_progress_bar=False), and the regression test now runs the real fit inside a Jupyter kernel.
  • SLIPPED Invented inspection findings passed the deterministic post-check (§3.1). Now a live eval.
  • SLIPPED Wrong-object auto-approval passed every test, because no test asked the question (§3.2). Now 26 golden cases.
  • SLIPPED The demo page stopped loading. A patch script wrote real newlines into an f-string in the cross-check panel. The fast suite passed because no test loaded the UI, and I had only smoke-tested the other page. Found while editing the same file. Now every page is parsed and rendered in the unit suite, and that test fails on the broken commit. It first failed for a different reason: run directly, the page's import claims loaded the page itself. The test now starts from the real entry point.
  • SLIPPED "A defect that covers 19.6% of the product" appeared only in the UI. The raw detail reached the LLM, which guessed its meaning (it is the share of the photo). Fixed by never sending internal details to the LLM, with a test.

How to read the confusion matrix

A plain classifier has a 2×2 matrix. Here it is 2×3, because the system may abstain: the middle column is "send to a human". So one accuracy number is not enough. Three questions matter instead:

  • How much does it automate? Screw: 106/160 claims (66%) are decided without a human; bottle: all 83.
  • When it decides alone, is it right? Screw 104/106 (98.1%); bottle 83/83. The 54 screw escalations all come from the uncertainty band, not from the wrong-object or cut-out checks (every test photo is a valid MVTec image).
  • Which errors remain, and what do they cost? One good screw was wrongly paid (1/41) and one defective screw was wrongly refused (1/119). The two cost different things: a wrong payment loses money, a wrong refusal loses a customer. The policy treats them symmetrically (both thresholds sit at a midpoint), which is a business decision to revisit.

The rows also show something the totals hide: good screws are harder than defective ones. 49% of good screws escalate against 29% of defective ones, consistent with the dataset confound below: every good test screw is darker than every defective one, and most are darker than any training image. For bottle, the perfect matrix rests on only 20 good images, so "0 wrongly paid" still has a 95% interval up to 16%.

Finding: the two screw errors are exactly the two images that define the band. good/005 is the highest-scoring good image and manipulated_front/012 the lowest-scoring defect. When held out, nothing in the calibration data is that extreme, so both land on the wrong side. Single extreme samples set the band, so it is brittle at its edges. Only cross-validation can show this, because the golden tests are in-sample for the deployed band.

Why the screw claims escalate: three hypotheses tested

HypothesisResultEvidence
Defect sizeSupportedEscalated defects are smaller (median mask area 0.24% vs 0.34%, Mann-Whitney p<0.0001); score correlates with defect area (Spearman ρ=0.48). thread_top has the largest defects and almost never escalates.
OrientationRejectedThe orientation estimator was unit-tested on synthetic screws. Training images cover all angles (largest gap 9.6°), and the distance to the nearest training angle does not predict score (ρ=0.10, p=0.52).
LightingConfound real, not the causeEvery good screw test image is darker than every defective one, and 26/41 are darker than any training image, so a dataset bias exists. A direct test: relighting the good images to the training median changed the median score 31.81 → 32.07, and escalations did not fall (17 → 21). (Measured with the original whole-image score; within good images, brightness still does not predict the product-only score: ρ=0.04.)

Next step (not done): screws are 1024 px but processed at 256 px, so a 0.2%-area defect covers only about 130 pixels. A higher-resolution refit would test this directly.

Does the heatmap point at the defect? (pointing game)

For each defective image: is the anomaly map's hottest pixel on the ground-truth defect (within 6 px at 256 px)? Bottle 63/63. Screw 102/119 (86%): manipulated_front 18/24, thread_side 18/23, scratch_head 20/24, scratch_neck 24/25, thread_top 22/23. 8 of the 88 approved screw defects were approved with the peak somewhere else: the right verdict, possibly for the wrong reason, the same pattern as the VLM descriptions (§3.5). The verdict metrics cannot show this; only a per-image check can. All 243 maps can be browsed, and filtered to these cases, on the app's Heatmap Gallery page.

Now the predicted mask is defined as heat at or above the approve threshold, inside the segmented product. Pixel AUROC (0.99) overstates localisation. It ranks every pixel of every image, and the vast majority are easy background, so it says little about whether the map traces the defect's shape. On bottles the predicted mask covers the break, but it is about 1.5x too large (median 5,716 vs 3,745 pixels at 256 px). On screws, every claim sent to a specialist has an empty prediction by construction (no heat reaches the approve threshold), and even approved screws reach a median IoU of only 0.28. The gallery suggests why: the true screw defects are tiny (a median of about 190 pixels on the 256 px map), and the blurred map draws a ring roughly twice their size around them, so a well-centred prediction still scores low. Caveat: the threshold is the decision threshold, not one tuned for segmentation; a threshold tuned for outlining (cross-validated, to avoid tuning on the test set) would score higher. Lowering it to the reject threshold does not help: the screw mask grows to about 8x the defect and the median IoU falls to 0.11. (python -m cv.localization regenerates these numbers into reports/localization.csv.)

Heat outside the screw: lint on the backdrop

Reviewing the gallery, I noticed heat "stains" on the background, away from the screw. Claude Code measured where the heat sits in every screw image (segmented screw with a 12 px margin, the defect outline, and the background) and zoomed into each background hotspot at full resolution. These hotspots are real objects, not model noise. One small curved fibre recurs in roughly 18 defect photos across four defect types, as if a single piece of lint lay on the backdrop throughout the session in which the defect images were captured. Dust specks and stray hairs account for most of the rest. PatchCore correctly flags them as anomalous, but they are not screw defects.

It is a dataset artifact that favours the defect class. Against the thresholds in use at the time (reject 32.1, approve 37.4), background heat above the reject threshold appears in 30/119 defective photos but only 1/41 good ones, and in 6 defective photos the background alone exceeds the approve threshold. Re-running the same 5-fold cross-validation with the score taken from the screw region only leaves AUROC unchanged (0.973 → 0.971) but changes 8 verdicts. 4 approved defects become escalations: they were approved because of lint, not the defect. 2 good screws that background specks had pushed into escalation become rejections, and 2 others move the opposite way because the band shifts. So about 4 of the 88 approved screw defects (5%) were right for the wrong reason, and the cross-validated metrics slightly flatter the model.

Acting on it: score only the segmented product

I decided to segment the product and ignore the backdrop. Claude Code implemented it so that it fails closed:

  • One segmentation everywhere (claims/segment.py): calibration, the live inspector, the analysis and the gallery call the same function, so they cannot drift apart. The claim score is the map's maximum inside the product plus a 12 px margin (the blurred map spills about 8 px).
  • An implausible cut-out escalates (segmentation_failed). The product's share of the frame must fall in a range calibrated on training images (screw 6–25%, bottle 31–94%).
  • The wrong-object guard still measures the whole photo. Otherwise a hazelnut "segmented as the product" could pass.
  • Bit-identical scores: thresholds are calibrated on maps saved as float16, and the screw approve threshold sits in a 0.06-wide gap, so the live inspector quantises its map the same way. Live CPU scores at both band edges matched the calibration exactly, and all 61 golden cases (including the 26 wrong-object photos) pass.

Result: AUROC 0.9705 → 0.9707. Compared with the whole-image score, 11 verdicts change. 4 defects that were approved now escalate (3 of them approved because of lint), 2 good screws that specks had pushed into review are rejected, and 5 good screws now escalate because the reject threshold moved down. Approve precision 84/85 and both error counts are unchanged; escalations rise from 47 to 54 (+15% human reviews). The trade is deliberate: more reviews, in exchange for no claim being approved by the backdrop.

6. Future work and scaling to the full benchmark

The agents are category-agnostic. The router, inspector, policy, responder, cross-check and graph contain no product names: they read the supported products from the calibration file, and the UI's product list is built from it. Adding a product means fitting one PatchCore model and calibrating its band. The immediate next phase is scaling the empirical evaluation across all 15 MVTec AD categories and the VisA dataset, specifically to benchmark the stability of the defect-area ceiling (the out-of-distribution guard) across diverse product classes (e.g., textiles, electronic components, and organic materials).

Why the ceiling in particular: its 1.5× margin and 10% floor were set from two products. In texture categories (carpet, leather, wood) the product fills the whole frame and real defects can be large, so the gap between the largest real defect and a wrong-object photo, which today is 43% vs 91–100% for bottle, may shrink or close. For each category the evaluation would report largest real defect area against wrong-object area, out-of-fold false-approve and escalation rates, and an adversarial golden set like the current 26 wrong-object cases.

Other next steps, each tied to a finding in this report:

  • Higher-resolution screw model: screws are processed at 256 px from 1024 px, and small defects drive the escalations (§5).
  • A safety margin around the band: both out-of-fold errors are the two images that define its edges (§5).
  • A calibration set of real customer photos: the largest untested gap (§4.2).
  • Localisation: a cross-validated segmentation threshold and a higher-resolution model, measured by IoU/Dice against the annotations (currently 0.18 median IoU on screws, §5).
  • Segmentation that survives real photos: the current Otsu cut-out assumes a dark product on a light backdrop (§4.2). A learned segmenter, or a model trained with backdrop clutter, would remove that assumption.
  • Per-category VLM evaluation with repeated runs: its defect answer changed on 1 in 6 escalations between identical runs (§3.5), so any VLM metric needs several runs and a stability figure.

Fine-tuned models in the decision itself. Today only PatchCore's score feeds the decision, and 34% of screw claims still go to a person (§5). The next step is to add fine-tuned AI models to the final decision, working alongside the deterministic rules, so that more cases across a wider variety of products and photos can be decided automatically. A model would get that role only after passing the same evaluation as the current system: cross-validated decision metrics, the adversarial golden set and repeated live runs. The rules would stay in place as guardrails: the wrong-object check, the coverage check and fail-closed error handling would still escalate anything the model cannot be trusted with. The vision-language model shows why that bar matters: its defect answer was right most of the time but changed between identical runs (§3.5), which is acceptable for a hint but not for a payment.

Building it with Claude Code (in the video)

Most of the video shows the product. One segment shows how it was built, because the product alone does not show how the AI was directed and checked. It makes four points, each covered in detail earlier in this document:

  • Framing. Design before code: the goal, what the AI may decide, what it may never decide, and how every result is tested were agreed and committed before implementation (§2).
  • Directing and iterating. Small steps, each change with its tests, each output reviewed before moving on (§2, iterations).
  • Questioning the output. The heatmaps looked wrong to me, so I asked for a gallery of all 243 results instead of trusting the summary metric. That led to the lint finding and to scoring only the segmented product (§5).
  • Catching Claude Code's own mistakes. An evaluation script silently overwrote its results when all 98 model calls had failed. It now records each call's error and refuses to write when more than 10% fail (§3.5). The other cases are in §3.7 and docs/dev-log.md.
